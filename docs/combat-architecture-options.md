# Combat 架构草稿（DAY_22）

状态：设计说明已由本人过目并认可轻量版 B、玩家技能范围及 A/C 取舍理由。尚未实现新架构、技能或效果，也未完成 LC-10 / BLU-22 正式评分。

## 现在怎样攻击

- 玩家：空格键本帧按下 → `PlayerAttack` 查询范围内的 Collider → 找 `EnemyHealth` → 调用 `TakeDamage`。`EnemyHealth` 在生命归零后通知 Dead 并销毁敌人。
- 敌人：`EnemyController` 判断状态、距离与冷却并进入 Attack → `EnemyAttack` 查询范围 → 找 `PlayerHealth` → 调用 `TakeDamage`，随后重置冷却并返回 Chase。`PlayerHealth` 管理血量与死亡时停机；R 重开由 `PlayerRestartController` 处理。
- 当前职责：`PlayerAttack` / `EnemyAttack` 发起攻击；`PlayerHealth` / `EnemyHealth` 管理各自血量与死亡；`EnemyController` 管理 FSM、路径更新和路径显示通知；`EnemyStatsConfig` 保存共享敌人参数。

当前攻击者分别依赖具体的 `EnemyHealth` / `PlayerHealth`。命中查询和扣血调用也都写在攻击脚本中。这在现有原型中能工作，不是必须立即重写的 bug。

## 三种实现路线

| 方案 | 核心做法 | 优点 | 风险 / 适用性 |
|---|---|---|---|
| A：维持具体依赖 | 近战和投射物各自找具体 Health 并扣血 | 当前改动最少 | 技能或目标种类增加时重复类型判断；适合作为成本基线 |
| B：小接口＋组合 | Health 类提供共同的可受伤能力；命中查询、伤害执行和技能释放分开 | 投射物可复用伤害入口；部件可单独测试 | 多一些连接代码；接口必须保持小，适合当前逐步扩展 |
| C：技能继承或可执行资产 | 共同基类 / ScriptableObject strategy 定义技能入口，近战和投射物分别实现 | 行为类型稳定时统一入口和 Inspector 配置方便 | 前期继承/资产层级较重；只在确有多态行为需求时采用 |

## 本人选择：轻量版 B

这不是“改用类”：现有 Health 和 Attack 本来就是类。B 的区别是给两类 Health 一个很小的共同能力约定，并把飞行或范围查询、命中筛选、效果执行分开。接口不做包含 Damage、Heal、Buff 等所有功能的万能入口。

暂不采用 A 作为 Week 4 主方向：未来投射物与范围技能会重复具体 Health 判断。暂不采用 C：现有功能还不足以证明继承层级或可执行资产策略的额外成本值得承担。以上拒绝理由由 AI 根据现有代码提出，已由本人认可。

### 责任边界

- 玩家输入：现有玩家输入组件或下一步最小技能执行入口。
- 命中与目标筛选：近战范围、投射物碰撞、范围减速各按自己的玩法判定；“可受伤”不等于“任何命中的对象都该受伤”。
- Damage / Slow 结果：由对应效果执行部分处理；Damage 调用目标的受伤能力。
- 生命与死亡：仍归 `PlayerHealth` / `EnemyHealth`；效果层不负责玩家停机、R 重开或敌人销毁。
- 共享配置：ScriptableObject 可保存伤害、范围、基础冷却等参数。
- 实例状态：每个施法者的 cooldown、当前目标和 Buff 剩余时间由运行时对象持有，不写进共享资产。
- 表现：动画、UI、音效由表现层响应结果；不让效果逻辑直接操作它们。
